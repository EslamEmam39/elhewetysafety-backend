# Authentication and Authorization

## Authentication

Use Laravel Sanctum Bearer Tokens. The Nuxt frontend authenticates against
the Laravel JSON API.

```text
Email + Password
→ FormRequest validation
→ AuthService
→ Repository finds User
→ Password verification
→ Sanctum Personal Access Token
→ Token returned to frontend
```

Protected requests send `Authorization: Bearer TOKEN`, and protected backend
routes use `auth:sanctum`.

## Login Architecture

Authentication logic does not belong in AuthController.

```text
AuthController
→ LoginRequest
→ AuthService
→ Repository
→ User
```

Token creation belongs to the authentication application layer.

The admin frontend authenticates through `POST /api/admin/login`. It reuses the
same `AuthController`, `LoginRequest`, credential checks, ban enforcement,
email-verification rule, token creation, and response shape as normal login,
while additionally requiring the `admin` role before issuing a token. A valid
non-admin account receives the same invalid-credentials failure as unknown or
incorrect credentials.

## Registration

Registration validates input, creates the User, assigns the `student` role,
creates a Student profile when required, and returns a public Resource. It does
not issue a Sanctum token; a user must verify their email before signing in.

Registration requires `username`, `phone`, `full_name_en`, `full_name_ar`,
`targeted_professional_field_code`, `email`, and a confirmed password. The
username, phone number, and email must be unique. The User UUID is generated by
the backend and must never be accepted from registration input. The selected
targeted professional field must exist and be active; clients obtain the
available choices from `GET /api/targeted-professional-fields`. UUIDs are
reserved for public User identity; reference data uses stable codes.

User creation, role assignment, and Student creation must use a database
transaction when they form one operation.

Registration dispatches a `UserRegistered` event after the transaction commits.
Its listener queues the email-verification OTP job, so email delivery never
blocks registration. The OTP must be
hashed at rest, single-use, purpose-specific, attempt-limited, and invalidated
when a replacement is issued.

## Email Verification

Users verify their email with an OTP sent to their registered address.

The resend and verification endpoints accept the user's email address and are
public so a user without a token can finish verification. Login rejects an
unverified user with a `403` response.

After successful email verification, the client takes the user to the login
screen. Registration has already collected and stored the confirmed password,
so verification must not issue a password-reset OTP. Password-reset OTPs are
reserved for the explicit forgotten-password flow.

- Verification and resend endpoints must be rate limited.
- A successful verification sets `email_verified_at` once.
- Expired, consumed, or invalid OTPs must fail with a Business Exception.
- OTP values must never be stored in plain text or returned by the API.

## Forgotten Password

Password-reset requests must return the same public response whether or not the
email exists, preventing account enumeration.

Password reset requires the email, OTP, new password, and password
confirmation. Successful reset consumes the OTP and revokes existing Sanctum
tokens.

Email-verification and password-reset OTPs must have different purposes and
must not be interchangeable.

## Banned Accounts

Login rejects banned Users with a `403` response before issuing a Sanctum
token. All authenticated API routes use the `not_banned` middleware, which
returns the same business error and exposes the optional `ban_reason` in the
structured error payload.

Admin-only endpoints ban and unban Users by public UUID. An administrator
cannot ban their own account. All administration endpoints use the
`/api/admin` prefix.

## Logout

Normal logout deletes only the current access token. Do not revoke every token
unless the requested feature explicitly logs out all devices.

## Device-Aware Login

User and Admin login require `device_uuid` and `device_name`; the optional
`device_platform` is descriptive only. The backend captures IP address and
User-Agent itself. A successful login registers or refreshes the Device before
issuing a Sanctum token and stores that Device relation on the token.

Authenticated Users can list and revoke their own Devices. Revocation removes
all Sanctum tokens belonging to the selected Device, including the current token
when that Device revokes itself. Admin operations use `devices.view` and
`devices.manage` through `DevicePolicy`. A Device UUID is an identifier, not
an authentication secret.

## Authorization

Use `spatie/laravel-permission` with initial roles `admin` and `student`.

Backend authorization is mandatory; frontend guards provide UX only. Never
trust client-provided user IDs, roles, permissions, prices, ownership, payment
status, enrollment status, or course access.

Use Policies, permission middleware, ownership rules, or Services as needed.
Admin operations use Laravel Policies backed by Spatie permissions. The admin
Role remains the route-level boundary, while permissions control individual
actions. Assigning the admin Role alone is insufficient until its permissions
have been seeded or assigned.

Role and Permission management endpoints are admin-only. Spatie remains the
single source of truth; do not add role or permission columns to users.

Admin user-management endpoints list, filter, view, and update Users by public
UUID. Permanent User deletion is intentionally unavailable so future financial,
access, and learning history cannot be removed accidentally. Ban/unban and role
assignment remain separate explicit operations.
Admin Student management uses separate `students.view`, `students.update`, and
`students.delete` permissions. Student deletion removes the profile and Student
Role only; it does not delete the owning User account.
Course administration uses `course-categories.view`,
`course-categories.manage`, `courses.view`, `courses.manage`,
`chapters.manage`, and `lessons.manage` permissions through Policies.
Payment gateway administration uses `payment-gateways.view` and
`payment-gateways.manage` through `PaymentGatewayPolicy`.
Order administration uses `orders.view` through `OrderPolicy`. Student Order
routes require Sanctum authentication, ban enforcement, and the `student` role;
ownership is enforced in `OrderService` and Repository queries.
Payment administration uses `payments.view` through `PaymentPolicy`. Student
Payment routes enforce ownership through the owning Order and never accept a
paid, failed, or refunded status from client input.
Enrollment administration uses `enrollments.view` and `enrollments.manage`
through `EnrollmentPolicy`. Student Enrollment queries are scoped to the
authenticated User, and protected Course content requires an active owned
Enrollment. Enrollment status is never accepted from student input.
Lesson Progress routes require Sanctum authentication, ban enforcement, the
Student role, and an active Enrollment for the Course. User IDs and completion
timestamps are never accepted from client input.
Course Review creation and update require the same authenticated active
Enrollment. Ownership scopes each Student's read, update, and delete operations.
Admin moderation uses `course-reviews.view` and `course-reviews.manage`
through `CourseReviewPolicy`; public requests receive visible reviews only.

## Local Seed Accounts

`DatabaseSeeder` creates deterministic accounts only when `APP_ENV=local`.
They use the password `password`: `admin@elhewety.test` for administration,
`student@elhewety.test` for normal authenticated flows,
`banned@elhewety.test` for ban enforcement, and
`unverified@elhewety.test` for email-verification enforcement. OTP values and
Sanctum tokens are never seeded; they must be issued through their API flows.
